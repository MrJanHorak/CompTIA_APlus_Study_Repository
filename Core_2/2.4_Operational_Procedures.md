## Documentation and Change Management

### Why Documentation Matters

Documentation is not optional — it is a professional requirement. It enables:

- Knowledge transfer when a technician leaves or is unavailable
- Consistent and repeatable repair processes
- Audit trails for compliance and legal purposes
- Reduced time to resolution when a similar issue recurs

### Types of Documentation

| Document                          | Purpose                                                      |
| --------------------------------- | ------------------------------------------------------------ |
| **Network diagram**               | Visual map of network topology, devices, and IP addresses    |
| **Baseline**                      | Recorded normal operating state; used to identify deviations |
| **Asset inventory**               | Database of all hardware and software in an organization     |
| **Acceptable Use Policy (AUP)**   | Rules governing how users may use company technology         |
| **Password policy**               | Requirements for complexity, length, and rotation            |
| **SLA (Service Level Agreement)** | Defines expected response and resolution times               |
| **Incident report**               | Formal record of a security incident or outage               |
| **Knowledge base (KB) article**   | Documented solution to a recurring issue                     |

### Change Management

Change management is a **structured, documented process** for making changes to production systems. Done correctly, it prevents outages, ensures rollback capability, and maintains accountability.

#### Example Change Management Workflow

1. **Identify the change** — What needs to change and why?
2. **Document the change** — Describe what will be modified
3. **Assess the risk** — What could go wrong? What is the impact if it fails?
4. **Establish a rollback plan** — How do you undo the change if needed?
5. **Get approval** — Change Advisory Board (CAB) or appropriate authority reviews and approves
6. **Schedule the change** — During a maintenance window with minimal user impact
7. **Implement the change** — Execute exactly as documented
8. **Verify the change** — Confirm the desired outcome; validate no new problems were introduced
9. **Document the outcome** — Record what was done, by whom, and the result

> **Practice:** Obtain the required approval before implementation. Emergency changes still follow the organization's documented emergency process.

#### Key Terms

| Term                            | Definition                                        |
| ------------------------------- | ------------------------------------------------- |
| **CAB (Change Advisory Board)** | Group that reviews and approves change requests   |
| **RFC (Request for Change)**    | Formal submission requesting a system change      |
| **Maintenance window**          | Scheduled time for changes, typically off-hours   |
| **Rollback plan**               | Documented steps to revert the change if it fails |
| **Sandbox / Test environment**  | Test the change before applying it to production  |

## Backup and Recovery

### Backup Types

| Type             | What Is Backed Up                              | Resets Archive Bit | Restore Complexity                    |
| ---------------- | ---------------------------------------------- | ------------------ | ------------------------------------- |
| **Full**         | All selected data                              | Yes                | Simple — one set                      |
| **Incremental**  | All changes since last full **or** incremental | Yes                | Complex — full + all incrementals     |
| **Differential** | All changes since last full backup             | No                 | Moderate — full + latest differential |

> **Exam Tip:**
>
> - **Incremental** = Fastest backup; slowest restore
> - **Differential** = Slower backup (grows over time); faster restore than incremental

### The 3-2-1 Backup Rule

- **3** copies of the data
- **2** different storage media types (e.g., local drive + cloud)
- **1** copy stored off-site (geographically separated)

### Recovery Objectives

| Term                               | Definition                                                        |
| ---------------------------------- | ----------------------------------------------------------------- |
| **RPO (Recovery Point Objective)** | Maximum acceptable data loss — how far back can you restore to?   |
| **RTO (Recovery Time Objective)**  | Maximum acceptable downtime — how long can the system be offline? |

### Backup Storage Locations

| Location            | Examples                             | Notes                                         |
| ------------------- | ------------------------------------ | --------------------------------------------- |
| **On-site (local)** | External HDD, NAS, tape library      | Fast recovery; vulnerable to site-wide events |
| **Off-site**        | Iron Mountain, secondary data center | Protected from local disasters                |
| **Cloud**           | Azure Backup, AWS S3, Backblaze      | Scalable; requires internet for recovery      |

## Safety Procedures

### Electrical Safety

| Practice                                                               | Reason                                             |
| ---------------------------------------------------------------------- | -------------------------------------------------- |
| **Power off and unplug** before opening any case                       | Prevents shock and component damage                |
| **Anti-static wrist strap (ESD strap)**                                | Discharges static; clip to unpainted metal chassis |
| **Anti-static mat**                                                    | Work surface that prevents ESD                     |
| **Handle PCBs by edges**                                               | Avoid touching chips, capacitors, and traces       |
| **Never work on powered equipment** when replacing internal components | Electrical safety hazard                           |

### ESD (Electrostatic Discharge)

- A static discharge as small as **10 volts** can damage sensitive components (threshold for damage; humans feel ~3,000V)
- Store components in **anti-static bags** when not installed
- Ground yourself before touching components

### Lifting and Ergonomics

- Lift with your legs, not your back
- Use a dolly or hand truck for heavy servers and UPS units
- Follow the workplace weight limit guidelines (commonly 50 lb / ~23 kg maximum for one person)

### Cable Management

- Route cables neatly to maintain airflow
- Use cable ties or velcro straps — avoid over-tightening
- Label cables for identification during future maintenance

### Equipment Disposal

| Material                                | Method                                                                     |
| --------------------------------------- | -------------------------------------------------------------------------- |
| **CRT monitors**                        | Hazardous waste — contain lead; must be recycled through certified e-waste |
| **Batteries**                           | Lithium, NiMH, lead-acid — all require special disposal                    |
| **Toner cartridges**                    | Manufacturer recycling programs                                            |
| **Circuit boards / old PCs**            | E-waste recycling centers                                                  |
| **Chemical solvents / cleaning agents** | Material Safety Data Sheet (MSDS/SDS) guidance; proper disposal required   |

## Environmental Controls

Data centers and server rooms have specific environmental requirements:

| Control                                | Target / Requirement                                                  |
| -------------------------------------- | --------------------------------------------------------------------- |
| **Temperature**                        | Follow equipment specifications and site environmental policy; monitor inlet temperature                  |
| **Humidity**                           | Follow equipment/site limits; low humidity increases ESD risk and condensation can damage equipment |
| **Hot/Cold Aisle Containment**         | Alternating hot-exhaust and cold-intake aisles for efficient cooling  |
| **Fire Suppression**                   | Follow the site’s approved fire plan; suppression system design depends on hazards and local requirements         |
| **Uninterruptible Power Supply (UPS)** | Battery backup; protects against power fluctuations and brief outages |
| **Power Distribution Unit (PDU)**      | Distributes AC power to rack-mounted equipment                        |
| **Surge Protector**                    | Protects against power spikes; not the same as a UPS                  |

## Communication and Professionalism

### Core Professionalism Principles

| Behavior                            | Description                                                               |
| ----------------------------------- | ------------------------------------------------------------------------- |
| **Active listening**                | Give full attention; do not interrupt; ask clarifying questions           |
| **Clear jargon-free communication** | Adapt technical language to the user's level of understanding             |
| **Set realistic expectations**      | Be honest about timelines; communicate delays proactively                 |
| **Follow up**                       | After resolution, confirm the user is satisfied; check for related issues |
| **Respect confidentiality**         | Do not discuss user data or issues outside proper channels                |
| **Avoid distractions**              | No personal calls or text messages during service calls                   |

### Dealing with Difficult Users

- **Remain calm and professional** regardless of the user's emotional state
- **Do not argue** — acknowledge frustration; redirect to problem-solving
- **Escalate** if a user becomes abusive or if the issue exceeds your scope

### Conflict Management

- Never promise what you cannot deliver
- If you cannot fix an issue, be honest and escalate to the appropriate team
- Do not make assumptions — confirm all symptoms and reproduce the issue before proposing a fix

> **v15 Update:** The 220-1202 objectives place increased emphasis on the **ethics of communication**, particularly in contexts involving user privacy, data security, and organizational reporting. Technicians must understand not just the technical fix, but the professional obligations that accompany it.

## Scripting Basics

The A+ exam does not require writing complex scripts, but technicians must understand basic scripting concepts and common use cases.

### Scripting Languages

| Language           | Platform                 | Common Use Cases                                                       |
| ------------------ | ------------------------ | ---------------------------------------------------------------------- |
| **PowerShell**     | Windows (cross-platform) | Automation of Windows admin tasks; Active Directory; batch deployments |
| **Batch / `.bat`** | Windows                  | Simple task automation; still widely used in enterprise environments   |
| **Bash**           | Linux / macOS            | Shell scripting; system automation; cron jobs                          |
| **Python**         | Cross-platform           | General purpose automation; data processing; network scripting         |
| **VBScript**       | Windows (legacy)         | Legacy IE automation; older enterprise scripts                         |

### Basic Scripting Concepts

| Concept         | Description                                                                |
| --------------- | -------------------------------------------------------------------------- |
| **Variable**    | Named storage for a value: `$name = "John"` (PowerShell)                   |
| **Loop**        | Repeat an action: `for`, `while`, `foreach`                                |
| **Conditional** | Execute code based on a condition: `if/else`                               |
| **Function**    | Reusable block of code with a name                                         |
| **Comment**     | Non-executing code for documentation: `#` (PowerShell/Bash), `REM` (Batch) |

### Common Automation Use Cases

- Bulk user creation in Active Directory
- Automated backup scripts
- Log parsing and alerting
- Software deployment across multiple machines
- Scheduled maintenance tasks (via Task Scheduler / cron)

## Remote Access Best Practices

| Best Practice                                 | Reason                                                      |
| --------------------------------------------- | ----------------------------------------------------------- |
| Use VPN before RDP                            | Avoids exposing RDP directly to the internet                |
| Enable NLA (Network Level Authentication)     | Requires authentication before establishing the RDP session |
| Use strong, unique passwords                  | Prevents brute-force attacks                                |
| Enable MFA on remote access accounts          | Adds a second layer even if credentials are compromised     |
| Limit RDP access to specific IPs via firewall | Reduces attack surface                                      |
| Disable remote access when not in use         | Removes the attack vector entirely                          |
| Audit remote access logs                      | Detect unauthorized access attempts early                   |

## Tickets, Assets and Evidence

### Support Records and Asset Lifecycle

A useful ticket identifies the requester, affected device/asset, symptoms, start time, business impact, severity and category. Keep chronological progress notes, tests, changes, escalation and a clear resolution. Record observed facts separately from theories, and protect credentials and private user content.

Asset records connect an asset tag/serial number to model, configuration, owner, assigned user, location, warranty and licensing. A CMDB records configuration items and relationships. Track procurement, deployment, maintenance, reassignment and retirement. Use onboarding/offboarding checklists to manage access and equipment consistently.

### Incident Escalation and Evidence

When prohibited content or a suspected compromise appears, follow the incident-response plan. Restrict your investigation to your role, preserve relevant data, and report through approved channels. Do not delete, reimage or browse unrelated private material while evidence preservation is required.

**Chain of custody** records who collected or handled evidence, when, why and each transfer. Use approved acquisition tools and integrity checks; keep originals protected. **Order of volatility** concerns collecting data that disappears quickly, such as memory or active connections, before persistent storage when the incident plan requires it. Power changes can destroy volatile evidence; consult the response team rather than apply a universal shutdown rule.

Respect retention requirements, NDAs, EULAs and personal versus business-use licenses. Open-source software also has license obligations. Handle personal identifiers, payment data and healthcare information only within authorized procedures.

## Artificial Intelligence in Support Work

AI tools can draft instructions, summarize tickets or suggest causes. Check organizational policy before using them and verify outputs against trusted documentation and observed system state.

- **Hallucinations:** A confident answer can invent a command, setting, source or diagnosis. Verify before applying it.
- **Bias:** Training data and prompts can produce uneven or misleading results; review decisions affecting users.
- **Privacy and security:** Do not submit credentials, customer data or private ticket contents to an unapproved public service.
- **Public versus private tools:** Deployment labels alone do not establish retention, training use, access controls or data location; check approved terms and configuration.
- **Appropriate use:** Attribute work where required, avoid plagiarism, and keep a human responsible for the repair and its validation.

Exercise: identify sensitive fields in a fictional ticket, decide whether the approved AI tool may receive them, and verify a suggested fix against the vendor's documentation before recording the result.

## Backup, Scripting and Remote-Access Extensions

A **synthetic full backup** is assembled from an existing full backup and later changes rather than rereading every source file. Test restores regularly, choose an in-place or alternative restore destination deliberately, and document retention/rotation such as grandfather-father-son. Archive-bit behavior in the earlier table is a traditional model; modern backup products may track changes differently.

JavaScript (`.js`) is another script type to recognize alongside PowerShell, batch, shell, Python and VBScript. Before running any script, inspect its source, permissions, targets and resource use; test on disposable data and plan rollback. Scripts can unintentionally expose data, change settings or exhaust resources.

Remote support can also use RMM, WinRM and SPICE, in addition to RDP, VPN, VNC, SSH and approved sharing tools. Confirm user consent and organizational authorization, verify the support operator, use approved secure access, and record the session's work.
